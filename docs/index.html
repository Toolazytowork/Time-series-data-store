End-to-End Write Flow

Follow the path of a write request as it guarantees durability via disk journaling and is sharded into the in-memory time-series index.

1

Client Entry Point

The application invokes WALManager::insert(metric_name, timestamp, value, tags). The WALManager orchestrates the transaction between disk durability and thread-safe in-memory cache.

2

Atomic Memory-Mapped Append

Before RAM insertion, WALWriter::append() is executed. It allocates serialized buffer chunks on the disk-backed virtual memory boundary using a lock-free std::atomic offset_ offset increment. The data is written directly to the memory-mapped boundary (mmap).

3

Database Core Routing & Shard Locking

Control is returned to TSDB::insert(). The metric name is hashed (std::hash) and mapped to one of the 16 independent Shard buckets to minimize lock contention. An exclusive lock is acquired using std::unique_lock.

4

Active Buffer Accumulation

The point is inserted into the specific TimeSeries::active_block buffer. The structure uses cache line alignment (alignas(16)) and tight packaging to minimize cache misses.

5

Gorilla Compressor Packing

Once the active vector exceeds the 1000-point threshold, it is packed on-the-fly. The GorillaCompressor serializes the block: timestamps are compressed using Delta-of-Delta variable-length framing; double-precision values are bit-cast to uint64_t and packed using XOR-based leading/trailing zero tracking. The compressed block is appended to the historical CompressedBlock array, and the active buffer is cleared.

End-to-End Query Flow

1

Index Lookup & Lock Acquisition

The query enters TSDB::query(metric_name). It hashes the metric name, identifies the shard, and acquires a std::shared_lock allowing concurrent read access without blocking other readers.

2

Selective Range Reconstruction

Under `query_complex`, the database uses the TagIndex (inverted key-value tag index) to compute the Boolean intersection of all matching metrics in O(1) time. For each target metric, only historical blocks overlapping the query range are loaded.

3

Streaming Decompressor

The selected blocks are run through GorillaCompressor::decompress. GorillaTimestampDecompressor and GorillaValueDecompressor stream bit sequences from the shared BitStreamReader, reconstituting raw vectors of data points with negligible overhead.

Q1: Can you explain the detailed bit-layout and implementation of the Gorilla float value compression? +
Interviewer
In your resume, you mention Gorilla floating-point compression. Walk me through the exact bitwise algorithm. How do you handle leading and trailing zero bits?
Candidate
Double-precision floats (64-bit) are first bit-cast to uint64_t. We compute the XOR of the current value with the previous value. If the XOR is 0, we write a single 0 bit to indicate no change.

If the XOR is non-zero, we write a 1 bit. We then evaluate whether the leading and trailing zeros fall inside the active window of the previous XOR calculation. If they do, we write a 0 control bit followed by the meaningful bits inside that existing window.

If the leading/trailing zeros do not fit in the previous window, we write a 1 control bit, followed by a 5-bit block representing the number of leading zeros (capped at 31), a 6-bit block representing the length of the meaningful bits (meaningful length - 1), and then write the meaningful bits.
Q2: What is false sharing, and how did aligning your shard structures to 64 bytes improve p99 tail latency? +
Interviewer
You aligned the Shard structure to 64 bytes. What is the physical memory rationale behind this, and how does it prevent latency spikes?
Candidate
False sharing occurs when independent variables accessed by different threads sit inside the same cache line (typically 64 bytes on modern CPUs). In our initial layout, the std::array<Shard, 16> layout placed shard locks contiguously. When thread A acquired a unique lock on Shard 0, it invalidated the cache line containing Shard 1, forcing Thread B on Shard 1 to reload its cache line from main memory, inducing a latency spike.

By applying alignas(64) to the Shard struct, we guarantee that each shard structure resides on a separate, dedicated cache line. This physical isolation reduced write p99 latency from **23µs to 17µs** (a **26% performance improvement**) under peak concurrent write workloads.
Q3: How does the custom mmap-based Write-Ahead Log (WAL) achieve zero-copy durability and lock-free append? +
Interviewer
How does your mmap WAL function without write-lock contention, and how did you verify the crash recovery time of under 0.74 seconds?
Candidate
Traditional file I/O requires buffer copies from user space to kernel page cache. Our WALWriter opens the file and calls mmap to map a fixed 64MB window directly into the process's virtual address space.

To support concurrent appending, we use an atomic write boundary pointer (std::atomic<size_t> offset_). When a writer thread inserts a record, it executes a lock-free fetch_add(total_size, std::memory_order_relaxed). This reserves a contiguous destination offset in virtual memory. The thread then copies the payload using a zero-copy std::memcpy to the mapped address without holding any global lock.

For crash recovery, the WALReader::recover parses the raw mmap buffer in-place on startup. Since it only processes linear binary structs directly from RAM mapped file bytes, we achieved recovery of **1,000,000 un-flushed data points in 734 milliseconds**!
Q4: How does the TagIndex perform fast multi-tag intersection queries? +
Interviewer
Describe the data structures of the inverted index. How do you evaluate a complex filter like tags: {host=server_0, env=production}?
Candidate
The TagIndex class stores an internal std::unordered_map<std::string, std::unordered_set<std::string>>. The key represents the serialized representation of tag-key and tag-value pairs: key:value. The value is a set of metric names matching that tag.

When query_complex is called with multiple tags, we fetch the set of metrics for the first tag. For subsequent tags, we look up their matching metric sets and compute the intersection of sets. This narrows the candidate list to only those metrics that satisfy all filters before executing range queries on individual time-series vectors.
