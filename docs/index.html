End-to-End Write Flow

Follow the path of a write request as it guarantees durability via disk journaling and is sharded into the in-memory time-series index.

1

Client Entry Point

The application invokes WALManager::insert(metric_name, timestamp, value, tags). The WALManager orchestrates the transaction between disk durability and thread-safe in-memory cache.

2

Atomic Memory-Mapped Append

Before RAM insertion, WALWriter::append() is executed. It allocates serialized buffer chunks on the disk-backed virtual memory boundary using a lock-free std::atomic offset_ offset increment. The data is written directly to the memory-mapped boundary (mmap).

3

Database Core Routing & Shard Locking

Control is returned to TSDB::insert(). The metric name is hashed (std::hash) and mapped to one of the 16 independent Shard buckets to minimize lock contention. An exclusive lock is acquired using std::unique_lock.

4

Active Buffer Accumulation

The point is inserted into the specific TimeSeries::active_block buffer. The structure uses cache line alignment (alignas(16)) and tight packaging to minimize cache misses.

5

Gorilla Compressor Packing

Once the active vector exceeds the 1000-point threshold, it is packed on-the-fly. The GorillaCompressor serializes the block: timestamps are compressed using Delta-of-Delta variable-length framing; double-precision values are bit-cast to uint64_t and packed using XOR-based leading/trailing zero tracking. The compressed block is appended to the historical CompressedBlock array, and the active buffer is cleared.

End-to-End Query Flow

1

Index Lookup & Lock Acquisition

The query enters TSDB::query(metric_name). It hashes the metric name, identifies the shard, and acquires a std::shared_lock allowing concurrent read access without blocking other readers.

2

Selective Range Reconstruction

Under `query_complex`, the database uses the TagIndex (inverted key-value tag index) to compute the Boolean intersection of all matching metrics in O(1) time. For each target metric, only historical blocks overlapping the query range are loaded.

3

Streaming Decompressor

The selected blocks are run through GorillaCompressor::decompress. GorillaTimestampDecompressor and GorillaValueDecompressor stream bit sequences from the shared BitStreamReader, reconstituting raw vectors of data points with negligible overhead.

Q1: How would you introduce the problem you were trying to solve and the motivation behind it? +
Interviewer
Welcome! Let's talk about your high-performance time-series database. To start, how would you introduce the problem you were trying to solve and the motivation behind it?
Candidate
In high-velocity monitoring environments (e.g. cloud telemetry, IoT streams), traditional databases bottleneck on write paths, disk-seek latencies, and high memory footprints. I designed an in-memory Time-Series Database (TSDB) in C++17 optimized for mechanical sympathy.

By using cache-aligned structures, lock-striped sharding, memory-mapped write-ahead logging (WAL), and Gorilla bitwise compression, we achieved a peak write throughput of 191,000+ writes/sec and read throughput of 189,000+ reads/sec on commodity hardware. Additionally, Gorilla compression compressed steady telemetries down to 0.27 bytes/point (a 91% average memory reduction).
Q2: Why choose sharded locking over a global lock or lock-free map, and how does false sharing affect it? +
Interviewer
You mentioned write throughput and concurrent access. Why did you choose sharded locking with 16 independent mutexes over a global lock or a completely lock-free concurrent hash map? And how does cache line false sharing impact this sharding?
Candidate
A global lock causes severe lock contention under concurrent load. A fully lock-free concurrent map avoids locks but makes range queries and multi-point transactions extremely complex to coordinate. I implemented a striped, sharded locking design (16 shards protected by std::shared_mutex), hashing metric names to distribute locks.

However, placing shards contiguously in a std::array leads to false sharing since adjacent locks reside on the same 64-byte L1 cache line. When Thread A acquires a lock on Shard 0, it invalidates the cache line on Thread B's core accessing Shard 1. To resolve this, I applied alignas(64) to the Shard structure. Under stress tests, this cache line alignment optimization reduced p99 write latency by 26% (from 23µs to 17µs).
Q3: How does the custom mmap WAL avoid disk write latency, and how does crash recovery perform? +
Interviewer
Speaking of durability, you built a custom WAL using memory-mapped files (mmap). Explain how this append-only logger avoids disk write latency during write bursts, and how your crash recovery performs.
Candidate
Traditional file writing uses the write() syscall, introducing page cache copy overhead and CPU context switches. Our WAL maps the log file directly into the virtual memory space using mmap, reducing writes to zero-copy pointer operations (std::memcpy).

To avoid lock contention on the log pointer, we use an atomic offset counter (std::atomic<size_t> offset_). Concurrent threads execute a lock-free fetch_add to claim their slice of mapped buffer and write their data without lock contention. During startup, the database scans the mmap space linearly in-place. Because data is stored in native binary representation, it recovers 1,000,000 data points in only 734 milliseconds (under 0.74 seconds).
Q4: What is the exact bit-layout of Gorilla Delta-of-Delta timestamps and float XOR values? +
Interviewer
Fascinating. Let's talk compression. You implemented the Gorilla compression algorithm. Can you explain the exact bit-layout details of the Delta-of-Delta for timestamps and XOR for floating point values? What compression rates did you achieve?
Candidate
For timestamps, we calculate the second-order delta-of-delta D = (T_i - T_{i-1}) - (T_{i-1} - T_{i-2}). We output:
  • D = 0 → bit 0.
  • D ∈ [-63, 64] → control bits 10 + 7 bits payload.
  • D ∈ [-255, 256] → control bits 110 + 9 bits payload.
  • D ∈ [-2047, 2048] → control bits 1110 + 12 bits payload.
  • Otherwise → control bits 1111 + 32/64 bits payload.
For floating-point values, we XOR with the previous value X = V_i ⊕ V_{i-1}:
  • X = 0 → bit 0.
  • X ≠ 0 → bit 1:
    • Window Reuse (bit 0): If leading/trailing zeros fall inside the previous XOR window → write 0 + payload bits.
    • New Window (bit 1): Write 1 + 5 bits leading zero count + 6 bits meaningful length + meaningful bits.
This achieves 0.27 bytes/point on steady telemetry (98.3% compression) and averages 91% footprint reduction across varied dynamic loads.
